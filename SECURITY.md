# Privacy and Security

## Reporting a vulnerability

If you discover a security vulnerability in this repository, **please do not open a public GitHub issue**. Instead, report it privately by emailing **<info@civicdatalab.in>** with the subject line `[SECURITY] DataSpace-data-ecosystem`.

Please include:
- A description of the vulnerability and its potential impact
- Steps to reproduce or a proof-of-concept (if available)
- Any suggested fix or mitigation

We will acknowledge your report within **5 business days** and aim to resolve confirmed vulnerabilities within **30 days**. We will credit reporters in the release notes unless you request otherwise.

## Scope

This repository contains:

- `audits/cds-audit` — a Python tool that calls the public CivicDataSpace API to audit dataset metadata and
  files (read-only; it does not write to the platform)
- `canonical_entities/` — scripts that call third-party boundary/geodata services and TOML/CSV/GeoJSON
  reference data
- `data_model/` — schemas and knowledge-graph definitions (no runtime service)
- `collaboratives/` — git submodules pointing at independent repositories, each with its own security scope
  and disclosure process; report vulnerabilities found in a collaborative's own code to that repository, not
  here

Security concerns relevant to this repository's own scope include: dependency vulnerabilities in
`audits/cds-audit`, unsafe handling of the CivicDataSpace API credentials/config an operator supplies, and
unintended exposure of data in checked-in sample/fixture files.

This repository does **not** itself run a web service, API, authentication layer, or database. `cds-audit` is
a client of the CivicDataSpace API; operators running it against production credentials are responsible for
securing those credentials and their own execution environment.

## Privacy

### What this repository processes

- `audits/cds-audit` reads dataset **metadata** and, in `--deep` mode, downloads and inspects resource files
  from the public CivicDataSpace catalogue. It does not itself collect personal data; whether the underlying
  datasets contain personal data is a property of the catalogue, not this tool.
- `canonical_entities/india/maps` processes **administrative-unit boundary data** (state/district/subdistrict/
  village polygons and codes) — no individual-level data.
- Fixture/sample data checked into `audits/cds-audit/tests/fixtures/` is **synthetic**, generated by
  `tests/make_fixtures.py`, and contains no real catalogue data.

### Upstream data sources and their terms

`canonical_entities/india/maps` pulls from India's NIC ArcGIS boundary service; `audits/cds-audit` pulls from
the CivicDataSpace API. Both carry their own terms of use. Operators are responsible for ensuring their use
complies with the relevant terms and with applicable data-protection law in their jurisdiction — including, in
the Indian context, the **Digital Personal Data Protection Act, 2023**.

### Collaboratives

Each repository under `collaboratives/` may process its own data, including data with different privacy
sensitivities than the tooling in this repo. Consult that collaborative's own repository for its privacy
scope and disclosure process.

## Dependencies

Each part of this repository declares its own dependencies (`audits/cds-audit/pyproject.toml`; the root
`pyproject.toml` only configures dev tooling). We recommend periodically auditing installed environments for
known CVEs using tools such as `pip-audit` or `safety`.

```bash
cd audits/cds-audit
pip install -e ".[dev]"
pip install pip-audit
pip-audit
```
